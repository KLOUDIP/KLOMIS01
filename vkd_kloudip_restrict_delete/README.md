# Restrict Record Deletion (Odoo 19)

> **1.2.0** - two additions for the case where a **Delete / trash icon
> survives** the restriction:
>
> 1. **`vkd_restrict_delete.extra_models` system parameter** - a
>    comma-separated list of any further technical model names to restrict, no
>    code change and no upgrade needed. This is the answer when the worksheet
>    list embedded in a task form is a *custom* model rather than a generated
>    `x_worksheet_*` one.
> 2. **View-level enforcement** - Odoo only applies its own check when the
>    arch has not set the attribute (`if not node.get(action)`), so a view
>    hard-coding `delete="1"` keeps the trash icon and the click then fails
>    with an `AccessError`. `ir.ui.view._postprocess_access_rights` is now
>    overridden to set `delete="False"` first, for restricted models and users
>    without the right only.
>
> **1.1.0** - coverage extended to **worksheets** and **stock transfers**
> (deliveries, receipts, internal transfers). Worksheet models are generated at
> runtime, one per template, so they are resolved from `worksheet.template`
> instead of being hard-coded, and the restriction is re-applied automatically
> when a new template is created. New dependencies: `stock`, `worksheet`.
>
> **1.0.2** - the optional view layer has been **removed**. Odoo 19 forbids
> group-restricted extension views (`_check_groups`: *"Inherited view cannot
> have 'groups' defined on the record"*), so the admin-only "put Delete back"
> view is not expressible. It is not needed either - see *How it works*.
>
> **1.0.1** - `ir.ui.view.groups_id` was renamed to **`group_ids`** in Odoo 19.
> The same rename applies to `ir.ui.menu`, `ir.actions.*` and `res.users` if you
> hit it elsewhere in the v19 migration.

Removes the **Delete** entry from the cog menu for every user except
administrators.

## Models covered

| Model | Covers |
|---|---|
| `helpdesk.ticket` | Helpdesk tickets |
| `project.task` | Project and Field Service tasks |
| `sale.order` | Quotations and sales orders |
| `account.move` | Customer invoices, vendor bills, credit notes, journal entries |
| `stock.picking` | Deliveries, receipts, internal transfers (all picking types) |
| `x_worksheet_*` | Every worksheet model generated by a `worksheet.template` |

The first five are listed in `RESTRICTED_MODELS` in
`models/ir_model_access.py` - edit that list to change them. Worksheets are
handled separately (see below) and can be switched off with
`RESTRICT_WORKSHEETS = False` in the same file.

Line models (`sale.order.line`, `account.move.line`, `stock.move`,
`stock.move.line`) are deliberately **not** touched - removing `unlink` there
would stop users from deleting lines while editing a document, including the
operation lines of a draft transfer.

## How it works

Odoo decides whether to show `Delete` from `ir.model.access`: when the user has
no `unlink` right on the model, the server strips the action out of the view
arch before sending it to the browser. So the reliable fix is to take the
delete right away, not to hide a button - and taking it away also blocks
XML-RPC / API deletes, not just the UI.

The module:

- Creates a group **Allow Record Deletion**, implied by *Settings /
  Administration* - so any user whose Role is `Administrator` inherits it
  automatically, and nobody else has it.
- Grants that group `unlink`-only access on the listed models.
- Runs `_kloudip_apply_delete_restrictions()`, which clears `perm_unlink` on
  **every other** access line of those models.

That is the whole mechanism. In `odoo/addons/base/models/ir_ui_view.py`:

```python
def _postprocess_access_rights(self, tree):
    ...
    for action, operation in (('create', 'create'), ('delete', 'unlink'),
                              ('edit', 'write')):
        if not node.get(action) and not model.has_access(operation):
            node.set(action, 'False')
```

Note `not node.get(action)`: never hard-code `delete="1"` anywhere, or this
check is skipped and users get a Delete button that throws `AccessError`.

### Worksheets

There is no single worksheet model. `worksheet.template` generates one model
per template (`x_worksheet_...`) at creation time, together with its own
`ir.model.access` lines granting full rights - including `unlink` - to the
worksheet users. Because those models have no fixed name and no xmlid, they
can be listed neither in `RESTRICTED_MODELS` nor in
`security/ir.model.access.csv`, so the module:

1. reads the current model names from `worksheet.template.model_id`
   (archived templates included) every time it applies the restriction;
2. **creates** the unlink-only access line for the *Allow Record Deletion*
   group on each of those models, since the CSV cannot;
3. clears `perm_unlink` on all their other access lines;
4. overrides `worksheet.template.create()` (see
   `models/worksheet_template.py`) to re-run the whole thing, so a template
   added *after* the module was installed does not arrive with a working
   Delete action.

If the `worksheet` module is not installed in your database, drop `"worksheet"`
from `depends` in `__manifest__.py` and remove the
`from . import worksheet_template` line in `models/__init__.py` - the rest of
the module works unchanged.

## The Delete button is still there - what to check

In order:

1. **Which model is it?** Turn on developer mode, hover the field that holds
   the list (or open one of its records) → **🐞 → View Fields / Fields View
   Get** shows the technical model name of the embedded list. Custom modules
   frequently store worksheets in their own model (`kloudip.worksheet`,
   `x_worksheet_line`, ...) rather than in the model generated by
   `worksheet.template`, and this module cannot guess that name.
2. **Add it to the parameter.** Settings → Technical → Parameters → **System
   Parameters** → `vkd_restrict_delete.extra_models` → put the model name in
   (comma-separated for several). Saving re-applies the restriction straight
   away; log out and back in to refresh the access cache.
3. **Check what is covered.** From an odoo shell, or a Server Action of type
   *Execute Python Code* on `ir.model.access`:

   ```python
   env['ir.model.access']._kloudip_check_delete_restrictions()
   ```

   It logs one line per model - `restricted`, `still granted to [...]`, or
   `MODEL NOT FOUND` (a typo in the parameter, or the module is not installed).
4. **Are you testing as an administrator?** Any user with *Settings /
   Administration* inherits *Allow Record Deletion* and is supposed to keep
   the button. Test with a plain Field Service / Helpdesk user.
5. **A hard-coded `delete="1"`** in the list view is handled from 1.2.0 on -
   but only for models the module knows about, so step 2 still comes first.

### Why there is no view layer

Odoo 19's `ir.ui.view._check_groups` rejects `group_ids` on any extension
view:

```python
@api.constrains('group_ids', 'inherit_id', 'mode')
def _check_groups(self):
    if view.group_ids and view.inherit_id and view.mode != 'primary':
        raise ValidationError(...)
```

So the "set `delete="0"` for everyone, put it back for admins" pattern can't be
built from inherited views any more - a plain `delete="0"` override would hide
the button from administrators too. The `groups` attribute the error message
points at works on elements *inside* the arch, not on root attributes. Access
rights are the only per-group lever, and they're the better one anyway.

## Install

```bash
# copy the folder into your addons path, then
odoo-bin -d <db> -u vkd_kloudip_restrict_delete -i vkd_kloudip_restrict_delete --stop-after-init
```

On Odoo.sh / SaaS: push to the addons repo, then **Apps → Update Apps List →
install "Restrict Record Deletion"**.

## Verify

1. Log in as a non-admin (e.g. a Helpdesk user). Open a ticket → cog menu:
   no `Delete`. Same on a task, a quotation, an invoice.
2. Inventory → any delivery, receipt or internal transfer → cog menu: no
   `Delete`. In the list view, tick a few transfers → the `Delete` entry in
   the ⚙ menu is gone as well (it follows the same access right).
3. Open a Field Service task with a worksheet → the worksheet record cannot be
   deleted; the task's Archive action still works.
4. Log in as an administrator → `Delete` is back everywhere.
5. As the non-admin, `env['stock.picking'].browse(id).unlink()` raises
   `AccessError`.
6. As an administrator, create a new worksheet template, then check
   Settings → Technical → Security → Access Rights for the new `x_worksheet_*`
   model: only the *Allow Record Deletion* line has **Delete Access** ticked.

## Caveats - please read

- **Upgrading a core module restores the right.** `sale`, `account`, `project`,
  `helpdesk` and `stock` ship their own `ir.model.access.csv`, which is
  reloaded on `-u sale` (or a version upgrade) and sets `perm_unlink` back to
  `1`. This module re-applies the restriction whenever *it* is upgraded, so
  include it in the same command: `-u sale,vkd_kloudip_restrict_delete`. A
  plain `-u all` is fine because this module loads after its dependencies.
- **Uninstalling does not roll back** the cleared `perm_unlink` flags. To
  restore them, upgrade the core modules:
  `-u sale,account,project,helpdesk,stock`. Worksheet models keep the extra
  access line created by this module; delete it manually if you want it gone.
- **Transfers**: Odoo already blocks deleting a done transfer; this makes
  draft/ready/waiting deliveries, receipts and internal transfers undeletable
  too. Users should **cancel** a transfer instead. Note that scrap orders,
  inventory adjustments and manufacturing orders are *not* covered - add
  `stock.scrap` / `mrp.production` to `RESTRICTED_MODELS` if you want them.
- **Invoices**: accountants will no longer be able to delete even *draft* or
  *cancelled* invoices. Posted invoices were already undeletable. If that is
  too strict, remove `account.move` from `RESTRICTED_MODELS` and upgrade the
  module.
- **Sales orders**: Odoo already blocks deleting a confirmed order; this makes
  draft/sent quotations undeletable too.
- **Worksheet templates themselves** (`worksheet.template`) are left alone -
  they are configuration records and already restricted to Field Service /
  Helpdesk administrators. Add `"worksheet.template"` to `RESTRICTED_MODELS`
  if you want the templates locked down as well.
- **Archive is the replacement action.** Tickets and tasks support Archive,
  which is what users should be pointed at once Delete is gone.
- **Module name**: the group is referenced as
  `vkd_kloudip_restrict_delete.group_allow_record_deletion` in
  `security/ir.model.access.csv`. If you rename the folder, update that column
  (the XML uses a module-relative ref and needs no change; the Python has a
  name-only fallback).

## No-code alternative (same effect, one database)

If you'd rather not install a module - useful for testing on
`kloudip-klomis01-klostag-19-10` first:

1. Turn on developer mode (Settings → General Settings → Developer Tools).
2. Settings → **Technical → Security → Access Rights**.
3. Filter `Model = helpdesk.ticket`. For every line listed, untick
   **Delete Access**.
4. Repeat for `project.task`, `sale.order`, `account.move`, `stock.picking`
   and each `x_worksheet_*` model.
5. Click **New** and add one line per model:
   - Name: `helpdesk.ticket.delete.admin`
   - Object: `helpdesk.ticket`
   - Group: `Administration / Settings`
   - Tick **Delete Access** only; leave Read/Write/Create unticked.
6. Log out and back in (or restart the worker) so the access cache refreshes.

Same caveat applies: a core-module upgrade will silently undo steps 3-4, and
every new worksheet template will arrive with its delete right intact - which
is the argument for the module version.
